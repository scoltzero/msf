## 已修复问题

### Provider 与 SSE

1. 前端忽略标准 SSE `event:` 字段，导致回复、工具状态、确认和错误全部静默丢失。
2. 工具流无条件拼接完整工具名，可能把 `list_msf_api` 变成重复的未登记名称。
3. 忽略 `tool_calls[].index`，多工具或稀疏分片可能错配。
4. Provider 空流、异常终止、过大文本和过大工具参数没有明确失败。
5. Provider 测试只要 HTTP 成功就算通过，没有校验目标文本或错误工具调用。
6. 未登记工具、无效工具 JSON、路由目录失败和最大轮次错误没有一致的终止事件与历史记录。

### 权限与确认

7. Admin API Token 可以进入原计划限定为浏览器管理员的助手入口。
8. 待确认动作存在并发双执行窗口，且冻结参数摘要没有在执行时验证。
9. 管理员在确认前切换到只读或关闭助手，旧动作仍可能按固定 `confirm_writes` 执行。
10. fallback 能力把部分 `DELETE`、安装、恢复、网络、nftables 和停止操作判成普通可逆写操作。
11. 确认卡片不展示冻结后的 query/body，用户无法确认真实参数。
12. 取消确认只清空前端对话，没有取消后端 pending action。
13. `auto_low_risk_writes` 实际仍要求确认，与设置名称不一致。

### 数据、密钥与审计

14. JSON 脱敏函数会反复命中同一敏感键，可能进入死循环；嵌套字段也无法可靠脱敏。
15. API Key 加密密钥首次并发创建可能互相覆盖；无效长度密钥会被静默替换。
16. `assistant_tool_runs` 表从未写入，工具审计只有空表。
17. 中文会话标题按字节截断会产生无效 UTF-8，历史会话可能被跳过。
18. 删除会话不会取消该会话的待确认动作和运行中请求。
19. 会话初始保存、最终保存和历史 JSON 解码错误被静默忽略。

### Skills、Memory 与上下文

20. 计划中的 `/opt/msf/configs/assistant/MEMORY.md` 从未加载，只有编译内置 Memory 生效。
21. 默认 Skill 只根据总行数判断是否初始化，部分失败后不会补齐。
22. Skill 临时文件名固定，并发写入可能互相干扰。
23. Skill 可以保存疑似 API Key、Token 或密码。
24. 最多 20 个、每个 6000 字符的 Skill 会被全部注入系统提示，可能超过模型上下文。
25. 单条用户消息、历史上下文和 Provider 输出缺少实际大小边界。
26. Memory 的工具说明与实际三个工具互相矛盾，低风险自动模式的文字也不准确。

### 前端状态与性能

27. 确认执行后 approval 状态未清除，可以重复点击旧确认卡片。
28. 快速重复发送可能在 React 状态提交前启动第二个请求。
29. 新会话只中止浏览器请求，没有通知后端停止当前会话。
30. 设置保存后全局 Orb/助手状态不刷新，需要重新加载页面。
31. 非管理员仍会挂载助手并产生一次必然 403 的状态请求。
32. 左上角 32px 标识启动第二个持续 GPU 渲染上下文，收益与成本不匹配；已改用同源 MIT Orb 海报资产。

## 仍存在的设计限制

1. 只有高价值能力拥有显式说明和参数 schema；其余约 369 条路由依赖运行时发现和保守 method/path 策略。后端权限仍生效，但模型可能需要多轮寻路才能得到正确 body/query。
2. 当前 Provider 协议只真正实现 OpenAI-compatible Chat Completions；`protocol` 字段尚未提供 Responses 等其他协议实现。
3. 会话、工具审计、过期待确认动作和 Skill `.trash` 尚无自动保留期限；长期运行需要增加配额与清理任务。
4. 本轮没有由审计代理替用户向外部 Provider 发送新的真实问题。最终工具闭环需要管理员在部署后重新发送原问题验证。

以上限制不会绕过管理员身份、后端 Policy 或确认机制，但应在后续迭代中单独规划。
